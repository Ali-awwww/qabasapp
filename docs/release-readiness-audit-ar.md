# تدقيق جاهزية النشر — مساعد المسلم

**الحالة:** تدقيق إنتاجي مستمر
**التاريخ:** 21 نوفمبر 2026
**المستودع:** `Ali-awwww/qabasapp`
**الفرع:** `main`

## النتيجة التنفيذية

المستودع الحالي ليس تطبيقًا صغيرًا مخصصًا للقرآن والصلاة فقط؛ بل هو تطبيق Android كبير مبني بـ Kotlin وJetpack Compose، يجمع وظائف إسلامية مع أجزاء واسعة من «مساعد المسلم» للإنتاج والوسائط والذكاء الاصطناعي. لذلك لا يصح إعلان الجاهزية للنشر قبل فصل النطاقات، تقليص السطح الوظيفي الظاهر للمستخدم، والتحقق من كل مسار فعليًا.

تم تحديث اسم العرض في موارد Android إلى **مساعد المسلم**، وتم إيقاف استخدام `debug.keystore` لتوقيع Release. أصبحت نسخة Release تعتمد على متغيرات بيئة لتوقيع إنتاجي منفصل، وتفشل بشكل مقصود إذا لم تُضبط تلك المتغيرات.

## ما تم التحقق منه

- التقنية: Kotlin + Jetpack Compose + Material 3 + Gradle.
- البناء المحلي: `assembleDebug` نجح بعد إنشاء مفتاح Debug محلي غير إنتاجي.
- APK الناتج: `app/build/outputs/apk/debug/app-debug.apk`.
- AVD موجود باسم `MuslimAssistantApi35`.
- تشغيل الـ AVD تعذر لأن بيئة Sandbox لا توفر `/dev/kvm`، ومحاكي x86_64 يتطلب تسريعًا عتاديًا. لذلك لم يتم الادعاء بإتمام فحص بصري على جهاز حقيقي.
- تم فحص نقاط الدخول والتنقل والثيم وملفات الشاشات ومخطط Supabase.
- مشروع Supabase `qabasapp` حي وحالته `ACTIVE_HEALTHY`.
- تم إصلاح خلل في `AgentConnectivityEngine` كان يعامل القيمة المحلية `__MISSING__` كمفتاح API صالح.
- `AgentQualityTest` نجح بعد الإصلاح، ومجموعة `testDebugUnitTest` الكاملة نجحت. ظهر تحذير تنظيف مؤقت من Robolectric بعد الاختبارات، لكنه لم يفشل المهمة.
- تم تطبيق أول طبقة فعلية من هوية Neo Islamic Noir على preset الثيم المشترك: أسود/أبيض كأساس، تركواز نيون للإجراء، وبنفسجي هادئ للإبراز.
- أُعيد تشغيل `lintDebug` بعد إصلاحات desugaring وApp Links وback وMedia3 وتوافق API؛ انتهى بنجاح مع **0 أخطاء، 758 تحذيرًا، و40 ملاحظة**. التحذيرات والملاحظات بقيت ظاهرة ولم يُنشأ baseline لإخفائها.

## فجوات حرجة قبل النشر

1. **التوقيع:** لا يجوز استخدام مفتاح Debug في Release. تم إغلاق هذا المسار في Gradle. يلزم توفير:
   - `RELEASE_KEYSTORE_PATH`
   - `RELEASE_KEYSTORE_PASSWORD`
   - `RELEASE_KEY_ALIAS`
   - `RELEASE_KEY_PASSWORD`
2. **الهوية:** توجد إشارات كثيرة إلى قبس واستوديو قبس داخل النصوص والمنطق وموارد التحديث. تحديث اسم التطبيق وحده لا يكفي؛ يلزم تدقيق شامل للنسخ، الروابط، رسائل التحديث، الأيقونة، سياسة الخصوصية، وبيانات المتجر.
3. **النطاق:** عدد المسارات والميزات كبير جدًا، وبعضها متعلق باستوديو الوسائط. المطلوب هو تأهيل المنتج المتكامل «مساعد المسلم» كحزمة واحدة للنشر؛ لذلك يجب توحيد الهوية والتنقل والتحقق من كل المسارات، مع إخفاء أو تعطيل المسارات غير المكتملة فقط، لا تقسيم المنتج إلى إصدار أول وآخر.
4. **اختبار الجهاز:** لم يُنفذ اختبار UI/تثبيت فعلي على AVD بسبب غياب KVM. يلزم تنفيذ الاختبار على جهاز Android فعلي أو بيئة CI/Cloud توفر تسريعًا عتاديًا.
5. **Release:** إعدادات `isMinifyEnabled` و`isShrinkResources` ما زالت معطلة. لا ينبغي تفعيلها قبل إضافة قواعد keep والتحقق من Supabase وRoom وCompose وFirebase، لكن لا ينبغي أيضًا اعتبار النسخة الحالية جاهزة للنشر.
6. **Lint debt:** lint نظيف من الأخطاء القاطعة حاليًا، لكن ما زالت هناك 758 تحذيرًا و40 ملاحظة، تشمل توطين نصوص hardcoded، locale formatting، بعض API warnings، وSharedPreferences؛ يلزم تقليصها تدريجيًا قبل إصدار المتجر.

## Supabase — نتائج الفحص الحي

أظهر Advisor في المشروع:

- 7 جداول عليها RLS دون سياسات (`app_secrets`, `app_update_delta_cache`, `bug_reports`, `platform_api_keys`, `promo_code_redemptions`, `promo_codes`, `user_feedbacks`). يلزم تحديد سياسة كل جدول قبل إضافة سياسات عامة؛ الجداول الحساسة يجب أن تبقى مغلقة افتراضيًا.
- View واحدة ذات `SECURITY DEFINER`: `community_profiles_public`.
- دالتان `SECURITY DEFINER` قابلتان للاستدعاء من `anon`، و13 دالة قابلة للاستدعاء من `authenticated`. يجب مراجعة صلاحيات EXECUTE والتحقق من `auth.uid()` داخل كل دالة قبل تعديلها.
- حماية كلمات المرور المسربة في Supabase Auth غير مفعلة.
- سياسات `user_push_tokens` تعيد تقييم دوال Auth لكل صف، وتحتاج تحسينًا باستخدام `(select auth.uid())` أو ما يناسب السياسة.
- توجد فهارس مكررة على `reels`، وفهارس غير مستخدمة تحتاج مراجعة مبنية على حركة الإنتاج لا حذفًا آليًا.

لم تُطبّق تغييرات مباشرة على قاعدة البيانات في هذه المرحلة، لأن إصلاح RLS والدوال يحتاج مصفوفة وصول لكل جدول ومسار مستخدم، وأي سياسة واسعة قد تكسر وظائف قائمة أو تكشف بيانات.

## خطة الاستوديو التالية

### المرحلة 1 — تثبيت نطاق المنتج المتكامل

- تعريف حزمة «مساعد المسلم» الكاملة: القرآن، الصلاة، الأذكار، القبلة، الحساب، الإعدادات، المصادقة، Supabase، ووظائف الاستوديو المتبقية إذا كانت مكتملة وقابلة للاستخدام.
- حصر جميع المسارات ومطابقة كل زر بمسار تنقل حقيقي وحالة تشغيل فعلية.
- إصلاح أو إخفاء الوظائف غير المكتملة أو غير الآمنة فقط، من دون اصطناع بيانات أو تقسيم المنتج إلى نطاقات إصدار.

### المرحلة 2 — الهوية وتجربة الاستخدام

- اعتماد نظام Neo Islamic Noir: أسود/أبيض كأساس، تركوازي نيون للإجراء الأساسي، بنفسجي أو ذهبي محدود للتأكيد، مع تباين WCAG.
- إعادة بناء الشاشة الرئيسية على مكونات مشتركة بدل تكرار البطاقات.
- مراجعة RTL، الخطوط العربية، حالات التحميل والخطأ والفراغ، ودعم reduced motion.

### المرحلة 3 — تكامل البيانات والأمان

- مطابقة كل Repository مع الجداول والدوال الفعلية.
- إعداد مصفوفة RLS لكل جدول.
- تقييد الدوال الحساسة، مراجعة `SECURITY DEFINER` و`search_path`، وتفعيل حماية كلمات المرور المسربة.
- عدم استخدام بيانات ثابتة بديلة على أنها بيانات حقيقية.

### المرحلة 4 — التحقق والنشر

- تشغيل unit tests وCompose screenshot tests.
- اختبار تسجيل الدخول، التسجيل، الضيف، استعادة كلمة المرور، القرآن، الصلاة، الأذكار، القبلة، الإعدادات، وفقدان الشبكة.
- اختبار على جهاز Android فعلي أو CI مزود بمحاكي متسارع.
- تجهيز AAB موقّع بمفتاح إنتاجي، وPlay Store checklist، وسياسة الخصوصية، ومواد المتجر.
